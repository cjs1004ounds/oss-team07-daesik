## 1. 확정된 제안

제안 이슈에서 확정된 내용을 옮겨 적은 것입니다. 2장부터는 확정 뒤 받은 피드백을 반영해 바꾼 내용입니다.

**한 줄 소개**
광운대 학생이 직접 남긴 추천글을 지도에서 보고, 거리와 가격, 작성자 구분으로 걸러 학교 주변 음식점을 찾는 웹 앱

**누가, 언제, 무엇 때문에 불편한가**
- 학교 주변 가게를 잘 모르는 광운대 신입생과 복학생이 대상
- 신입생은 아는 선배가 없으면 어디가 괜찮은지 물어볼 곳이 없음
- 복학생은 휴학하는 동안 가게가 새로 생기거나 없어져서 예전에 알던 정보가 맞지 않음

**지금은 어떻게 해결하고 있나**
- 선후배 입소문: 아는 사람이 있어야만 정보를 얻을 수 있음
- 에브리타임 같은 커뮤니티 글: 금방 묻혀서 찾기 어렵고, 오래된 글에는 폐업한 가게가 섞여 있음
- 네이버지도, 카카오맵 리뷰: 학생이 아닌 손님의 리뷰와 광고성 리뷰가 섞여 있고, 도보 거리나 1인 가격 같은 학생 기준으로 거를 수 없음

**ChatGPT에게 직접 묻는 것과 무엇이 다른가**
- 데이터가 쌓임: 학생들이 직접 가 보고 남긴 기록이 쌓이며, 최근에 생기거나 없어진 가게도 반영됨
- 여러 사람이 함께 씀: 여러 학생이 같은 지도에 기록을 남기고, 모두 같은 결과를 봄
- 화면이 더 빠름: 질문을 매번 입력하지 않고, 지도와 필터에서 골라 바로 확인

**가장 먼저 완성할 기능**
지도에서 가게를 검색해 고른 뒤 추천을 남기면, 그 가게 마커를 눌렀을 때 추천 목록이 표시됨

## 2. 교수님 피드백과 바뀐 방향

제안은 그대로 확정되었지만, 다음 의견을 받았습니다.

> 이 서비스는 추천글이 얼마나 쌓이느냐에 따라 거의 모든 것이 결정될 것 같다. 지금은 팀원들이 시드 데이터를 넣는 것 외에는 학생들이 여기에 글을 남길 이유가 잘 보이지 않는다. 에브리타임에 한 줄 쓰는 것보다 입력할 것도 많다. 누가, 어떤 마음으로, 얼마나 쉽게 글을 남기게 될지를 먼저 생각해 보면 좋겠다. LLM도 요약보다는 글을 쉽게 남기게 하는 쪽에 쓰는 방법을 생각해 보면 좋겠다.

이 의견에 대한 팀의 답은 아래와 같습니다.

| 질문 | 처음 제안 | 바꾼 방향 |
| --- | --- | --- |
| 누가 쓰나 | 구분하지 않음 | 쓰는 사람은 학교를 1년 이상 다닌 재학생, 읽는 사람은 신입생과 복학생으로 나눠서 설계 |
| 어떤 마음으로 쓰나 | 후배를 돕고 싶은 마음에 기대 | 본인에게 쓸모 있는 일을 하다 보면 기록이 남게 함. 친구들과 밥 먹을 곳을 정하는 일을 앱에서 하면 그 결과가 기록이 됨 |
| 얼마나 쉽게 쓰나 | 별점, 가격, 추천글, 작성자 구분을 모두 입력 | 가장 짧은 기록은 버튼 한 번, 글을 남기는 경우도 한 줄이면 끝 |
| 평가 방식 | 별점 1~5 | "또 갈래요" 또는 "글쎄요" 두 가지 중 하나 |
| LLM 역할 | 쌓인 추천글을 한 줄로 요약 | 한 줄 추천에서 가격과 태그를 뽑아 입력 칸을 미리 채움 |
| 처음에 글이 없는 문제 | 시드 데이터 | 시드 데이터에 더해, 글이 없는 가게도 지도에는 표시하고 "첫 기록 남기기"로 유도 |

작성자 구분 필터(신입생, 복학생, 학번)는 입력할 것을 줄이기 위해 첫 버전에서 뺐습니다.

## 3. 사용 흐름

### 3.1 쓰는 사람: 기록을 남기는 세 가지 길

부담이 적은 순서입니다. 셋 다 로그인 없이 됩니다.

**길 1. 같이 정하기 (글 없이 기록이 남음)**

1. 한 명이 방을 만들고 링크를 단톡방에 올립니다.
2. 각자 링크로 들어와 후보 가게에 투표합니다.
3. 방을 만든 사람이 투표를 마감하면 표가 가장 많은 가게가 정해지고, 방문 기록이 하나 생깁니다.
4. 다녀온 뒤 같은 링크에서 "또 갈래요" 또는 "글쎄요"를 누릅니다.

투표 현황은 실시간 통신 없이, 화면이 몇 초마다 서버에 다시 물어보는 방식으로 갱신합니다.

**길 2. 다녀왔어요 (버튼 한 번)**

지도에서 가게를 누르고 "또 갈래요" 또는 "글쎄요"를 누르면 끝입니다.

**길 3. 한 줄 추천 (한 줄 쓰면 나머지는 채워짐)**

가게를 고르고 한 줄을 씁니다.

```
제육 7천원인데 양 많음 혼밥하기 좋음
```

서버가 이 문장을 LLM에 보내 1인 가격(7000)과 태그(양 많음, 혼밥)를 뽑아 입력 칸에 채웁니다. 작성자는 확인하고 저장을 누릅니다. 음식 종류는 가게 검색 결과에 들어 있는 분류를 그대로 써서 따로 입력하지 않습니다.

### 3.2 읽는 사람: 가게를 찾는 길

1. 지도를 열면 학교에서 걸어서 15분 안에 있는 가게가 표시됩니다.
2. 1인 가격 상한, 음식 종류, 태그로 거릅니다.
3. 가게를 누르면 방문 횟수, 또 가겠다는 비율, 한 줄 추천 목록이 보입니다.

### 3.3 구글 폼과 ChatGPT로 대신할 수 없는 이유

제안 단계의 LLM 검토에서 "구글 폼으로 글을 모아 CSV를 ChatGPT에 올리면 된다"는 지적을 받았습니다. 바뀐 방향에서는 다음이 다릅니다.

- 같이 정하기는 여러 사람이 같은 방에 표를 넣고 같은 집계를 보는 일이라, 한 사람과 대화하는 ChatGPT로는 할 수 없습니다.
- 기록은 밥 먹을 곳을 정하는 과정에서 생깁니다. 누군가 글을 모으고 정리해서 다시 올리는 사람이 필요 없습니다.
- 남긴 즉시 모두의 지도에 반영됩니다.

## 4. 기능과 우선순위

| 순위 | 기능 | 내용 | 목표 시점 |
| --- | --- | --- | --- |
| P0 | 가게 검색 | 가게 이름으로 검색해서 고르기 | 중간발표(11/19) |
| P0 | 한 줄 추천 저장과 조회 | 가게에 한 줄 추천을 남기고, 지도에서 가게를 눌러 확인 (LLM 없이 직접 입력) | 중간발표(11/19) |
| P0 | 지도와 필터 | 도보 시간, 1인 가격, 음식 종류로 거르기 | 13주차(11/26) |
| P0 | 한 줄 자동 채움 | LLM이 한 줄에서 가격과 태그를 뽑아 입력 칸 채우기 | 13주차(11/26) |
| P0 | 다녀왔어요 | 버튼 한 번으로 방문 기록 남기기 | 13주차(11/26) |
| P0 | 배포 | Docker로 실행, 공개 주소로 접속 | 14주차(12/3) |
| P1 | 같이 정하기 | 방 만들기, 투표, 마감, 다녀온 뒤 응답 | 13주차(11/26) 목표, 늦어도 배포 전 |
| P2 | 내 기록 | 내 브라우저에서 남긴 기록만 모아 보기 | 여유가 있으면 |
| P2 | 문장으로 찾기 | "만 원 이하 국밥" 같은 문장을 필터 조건으로 바꾸기 | 여유가 있으면 |

가장 먼저 완성할 기능은 "가게를 검색해 고르고, 한 줄 추천을 남기고, 지도에서 그 가게를 눌러 확인하기"입니다. 이 흐름이 끝까지 동작한 뒤에 다른 기능을 붙입니다.

같이 정하기는 피드백에 대한 핵심 답이지만 화면과 API가 가장 많이 필요합니다. 그래서 첫 기능을 먼저 끝낸 뒤에 시작하고, 13주차까지 투표와 마감까지만 되어도 기록이 남도록 범위를 잡았습니다.

## 5. 계산 규칙

화면 코드와 다른 파일에 순수 함수로 두고, 화면 없이 테스트합니다.

| 번호 | 규칙 | 예시 (입력 → 결과) |
| --- | --- | --- |
| R1 | 도보 시간 = 학교 기준점과 가게 사이 직선거리 / 분당 67m, 올림 | 직선거리 500m → 8분 |
| R2 | 도보 시간이 15분을 넘는 가게는 제외 | 15분 → 포함, 16분 → 제외 |
| R3 | 1인 가격 상한, 음식 종류, 태그로 거르기. 가격 기록이 없는 가게는 가격 필터를 걸면 제외 | 상한 8000, 가게 평균 7000 → 포함 |
| R4 | 또 가겠다는 비율 = "또 갈래요" 수 / 전체 응답 수. 응답이 3개 미만이면 "기록 부족" | 또 갈래요 3, 글쎄요 1 → 75% |
| R5 | 정렬: 또 가겠다는 비율이 높은 순, 같으면 도보 시간이 짧은 순. "기록 부족"은 뒤로 | |
| R6 | 한 줄 추천 검사: 5~100자, 가격은 1,000~100,000 사이 정수이거나 비어 있음, 태그는 정해 둔 목록 안에서 최대 3개 | 가격 -500 → 거절 |
| R7 | 같은 익명 ID는 같은 가게에 하루 한 번만 기록 가능 | 같은 날 두 번째 → 거절 |
| R8 | 투표 집계: 표가 가장 많은 가게 선택, 동점이면 도보 시간이 짧은 가게. 한 사람은 한 방에서 한 표 | A 2표, B 2표, A가 더 가까움 → A |
| R9 | 같은 방에서 최근 7일 안에 정해졌던 가게는 후보에 "최근에 감"으로 표시 | |
| R10 | 가게 검색 결과는 같은 검색어에 대해 10분 동안 저장된 결과 사용 | 9분 뒤 → 저장된 결과, 11분 뒤 → 다시 호출 |
| R11 | LLM 응답 검사: 가격이 R6 범위를 벗어나거나 목록에 없는 태그는 버림 | 태그 "최고맛집" → 버림 |

태그 목록(초안): 양 많음, 혼밥, 가성비, 빨리 나옴, 조용함, 단체 가능, 늦게까지 함, 매움

## 6. 서버와 API

### 6.1 구조

```
브라우저 (HTML/CSS/JavaScript, 카카오맵 SDK)
    |  fetch
Express 서버
    |-- 계산 규칙 함수 (순수 함수, 테스트 대상)
    |-- 저장 모듈  --> JSON 파일
    |-- 카카오 로컬 API (가게 검색)
    |-- LLM API (한 줄 자동 채움)
```

- API 키(카카오 REST 키, LLM 키)는 서버 환경 변수로만 둡니다. 브라우저에서 쓰는 카카오맵 JavaScript 키는 허용 도메인을 제한합니다.
- 저장은 `store.add()`, `store.find()` 같은 저장 모듈을 거칩니다. 나머지 코드는 JSON 파일인지 다른 저장소인지 모르게 해서, 배포 환경에 따라 바꿀 수 있게 합니다.

### 6.2 API (초안)

| 메서드 | 경로 | 하는 일 | 순위 |
| --- | --- | --- | --- |
| GET | /api/health | 서버 상태 확인 | P0 |
| GET | /api/places/search?q= | 카카오 로컬 API로 가게 검색 (R10 캐시) | P0 |
| GET | /api/places | 기록이 있는 가게 목록. 필터와 정렬 적용 (R1~R5) | P0 |
| GET | /api/places/:id | 가게 상세: 방문 횟수, 비율, 한 줄 추천 목록 | P0 |
| POST | /api/reviews | 한 줄 추천 저장 (R6, R7) | P0 |
| POST | /api/reviews/draft | 한 줄을 받아 가격과 태그 초안 반환 (LLM, R11) | P0 |
| POST | /api/visits | "또 갈래요" 또는 "글쎄요" 기록 (R7) | P0 |
| POST | /api/rooms | 방 만들기, 방 코드 발급 | P1 |
| GET | /api/rooms/:code | 방 상태: 후보, 표, 마감 여부 | P1 |
| POST | /api/rooms/:code/votes | 투표 | P1 |
| POST | /api/rooms/:code/close | 마감하고 가게 결정 (R8), 방문 기록 생성 | P1 |

요청과 응답 형식은 구현 전에 이슈에서 합의하고 `docs/api.md`에 적습니다.

### 6.3 저장하는 데이터

| 파일 | 내용 |
| --- | --- |
| places.json | 기록이 한 번이라도 남은 가게: 카카오 장소 ID, 이름, 위도, 경도, 분류 |
| reviews.json | 한 줄 추천: 가게 ID, 문장, 1인 가격, 태그, 익명 ID, 작성 시각 |
| visits.json | 방문 응답: 가게 ID, 또 갈래요 여부, 익명 ID, 방 코드(있으면), 시각 |
| rooms.json | 방: 코드, 후보 가게, 표, 마감 여부, 정해진 가게 |
| seed/ | 팀원이 직접 가 본 가게의 시드 데이터. 저장소에 포함해서 재배포해도 남음 |

무료 호스팅은 재시작하면 파일이 초기화될 수 있습니다. 사용자 기록을 유지하는 방법은 14주차에 배포할 서비스의 영구 저장소 지원 여부를 확인한 뒤 정합니다.

## 7. LLM을 쓰는 곳

한 줄 추천을 남길 때 입력을 줄이는 데에만 씁니다.

| 항목 | 내용 |
| --- | --- |
| 호출 위치 | 서버의 `POST /api/reviews/draft` |
| 보내는 것 | 사용자가 쓴 한 줄, 가게 이름과 분류, 허용 태그 목록 |
| 받는 것 | `{ "price": 7000, "tags": ["양 많음", "혼밥"] }` 형식의 JSON |
| 검사 | R11로 범위 밖 가격과 목록에 없는 태그를 버림 |
| 쓰는 곳 | 입력 칸에 미리 채움. 사용자가 확인하고 저장해야 반영됨 |
| 실패하면 | 칸을 비워 두고 직접 입력해서 저장. 조회, 필터, 투표는 LLM과 무관하게 동작 |

LLM이 하지 않는 일: 가게 추천, 순위 계산, 가게 정보 생성. 이 부분은 저장된 기록과 5장의 규칙으로만 계산합니다.

## 8. 개인정보와 악용 방지

- 회원가입과 로그인이 없습니다. 이름, 학번, 연락처를 받지 않습니다.
- 브라우저에 처음 들어오면 무작위 익명 ID를 만들어 브라우저 저장소에 둡니다. 중복 기록을 막는 데에만 씁니다.
- 한 줄 추천은 공개되므로, 입력 칸에 "이름이나 연락처를 쓰지 마세요"라고 안내합니다.
- 같은 익명 ID는 같은 가게에 하루 한 번만 기록할 수 있습니다(R7). 브라우저 저장소를 지우면 우회할 수 있다는 한계가 있습니다.
- 저장소와 배포된 앱은 공개이므로, 시드 데이터에는 공개해도 되는 내용만 넣습니다.

| 크롤링 없음 | 카카오 공식 API만 사용 |

| 실시간 통신 없이 주요 기능 동작 | 투표 현황은 주기적 조회로 갱신 |

## 12. 협업 규칙

### 브랜치

| 종류 | 용도 | 예시 |
| --- | --- | --- |
| main | 항상 실행되는 기본 브랜치 | |
| feat/* | 새 기능 | feat/review-draft-api |
| fix/* | 버그 수정 | fix/walk-time-rounding |
| docs/* | 문서 | docs/api-spec |
| test/* | 테스트 | test/vote-tally |
| chore/* | 설정, 환경 | chore/express-setup |

- main에 직접 푸시하지 않습니다.
- 브랜치는 이슈 하나 단위로 만들고, 합친 뒤 지웁니다.

### 작업 순서

1. 이슈를 만들고 담당자를 정합니다.
2. 최신 main에서 브랜치를 만듭니다.
3. 작은 단위로 커밋하고 테스트를 돌립니다.
4. PR을 열고 본문에 `Closes #번호`를 적습니다.
5. 팀원 한 명 이상이 승인하면 합칩니다.

### 커밋 메시지

`종류: 내용` 형식으로 씁니다. 종류는 feat, fix, docs, test, refactor, chore 중 하나입니다.

```
feat: 한 줄 추천 저장 API 추가
fix: 도보 시간 올림 처리 수정
test: 투표 동점 처리 테스트 추가
```

### 리뷰할 때 보는 것

- 이슈의 완료 기준을 채웠는가
- 합의한 API 형식을 깨지 않는가
- 계산 규칙이 화면 코드와 분리되어 있고 테스트가 있는가
- API 키, .env, 개인정보가 들어가지 않았는가

## 13. 테스트

계산 규칙마다 정상, 경계값, 오류 사례를 씁니다.

| 대상 | 확인할 것 |
| --- | --- |
| 도보 시간 (R1, R2) | 0m, 정확히 15분 거리, 15분을 조금 넘는 거리, 좌표가 잘못된 경우 |
| 필터와 정렬 (R3, R5) | 가격 기록이 없는 가게, 조건에 맞는 가게가 없는 경우, 비율이 같은 경우 |
| 비율 (R4) | 응답 0개, 2개, 3개, 전부 "글쎄요" |
| 입력 검사 (R6) | 4자와 5자, 100자와 101자, 음수 가격, 목록에 없는 태그, 태그 4개 |
| 중복 제한 (R7) | 같은 날 두 번, 자정을 넘긴 뒤, 다른 가게 |
| 투표 (R8) | 표가 없는 경우, 동점, 한 사람이 두 번 투표 |
| 캐시 (R10) | 10분 직전과 직후, 다른 검색어 |
| LLM 응답 (R11) | JSON이 아닌 응답, 범위 밖 가격, 목록에 없는 태그, 호출 실패 |

LLM을 쓰는 부분은 LLM 응답을 가짜 값으로 바꿔서 자동 테스트하고, 실제 호출은 손으로 확인합니다.
